# Implementation Plan: Marketplace Listing Quality Reviewer

## 1. Executive Summary & System Overview

The **Marketplace Listing Quality Reviewer** is a full-stack, human-in-the-loop content evaluation platform. It assists marketplace operators and sellers by screening product/service listings against strict marketplace policies and brand guidelines before publishing. 

### Key Objectives
* **Reliable Deterministic Pre-Screening:** Immediate detection of invalid schemas, negative prices, out-of-bounds text lengths, unsupported categories, and duplicates without invoking LLMs.
* **Context-Aware Policy Retrieval:** Category matching and keyword relevance scoring to feed only pertinent policy rules into the AI prompt.
* **AI-Assisted Quality Auditing:** Identification of misleading claims, prohibited items, unverified claims, and stylistic deficiencies with strict citation requirements.
* **Human-in-the-Loop Workbench:** Complete operator control to approve, edit, or reject AI-suggested rewrites, creating audited revisions without destroying original inputs.
* **Resilient Batch Processing & Full Auditability:** Fault-tolerant batch imports where a single failure does not block the remaining listings, backed by append-only PostgreSQL review-history records.

## 4. Deterministic Validation & Policy Retrieval Engine

### 4.1 Deterministic Validation Rules (Executed prior to LLM)
1. **Required Fields:** `title`, `description`, `category`, `price`, `seller`.
2. **Category Allowlist:** Limited and documented set:
   * `ELECTRONICS`, `FASHION_APPAREL`, `HOME_KITCHEN`, `HEALTH_WELLNESS`, `COLLECTIBLES_ART`, `SERVICES`.
3. **Price Validation:** Must be positive number, max precision 2 decimals ($0.01 to $999,999.99).
4. **Length & Structure Boundaries:**
   * Title: 10 to 150 characters.
   * Description: 30 to 3,000 characters.
   * Tags: Max 10 tags, each 2 to 30 characters.
5. **Duplicate Detection:**
   * `normalizedKey = sha256(trim(lower(seller)) + "::" + category + "::" + normalizeWhitespace(lower(title)))`
   * Check both the submitted batch and existing database records. An exact normalized-key match is a blocking validation error; no AI request is made for that listing.

### 4.2 Policy Retrieval & Scoring Engine
Instead of dumping the entire rulebook into the context window, the system selects relevant rules:
* **Step 1: Category Match:** Fetch all universal policies (`category = "ALL"`) plus policies matching the listing's specific category.
* **Step 2: Keyword Scoring:**
  * Tokenize listing title, description, and attributes into unique terms.
  * Score each policy: $\text{Score} = (\text{CategoryMatchWeight} \times 3) + \sum (\text{KeywordOccurrences})$.
* **Step 3: Top-K Context Selection:** Inject the top $N$ policy sections (e.g., top 5–8 relevant policies) into the LLM system prompt along with their exact `code`.

## 5. AI Review Pipeline & Citation Guardrails

### 5.1 AI Structured Output Schema
The AI is instructed to act strictly as an auditor and return JSON adhering to this schema:

```json
{
  "summary": "High-level summary of review",
  "overallCompliance": "NEEDS_CHANGES",
  "findings": [
    {
      "field": "title",
      "issueType": "UNVERIFIABLE",
      "severity": "HIGH",
      "explanation": "Claim of '100% Guaranteed Cure for Pain' is an unapproved medical claim.",
      "supportingEvidence": "Listing title contains '100% Guaranteed Cure'",
      "policyCode": "POL-HEALTH-01",
      "suggestedWording": "Advanced Pain Relief Comfort Cushion"
    }
  ]
}
```

### 5.2 Citation Guardrails & Anti-Hallucination Checks
Before saving AI findings into PostgreSQL, the backend enforces:
1. **Strict Code Verification:** Every `policyCode` returned by the LLM *must* exist within the `retrievedPolicyCodes` array sent in that specific prompt. If the model cites a non-existent or un-retrieved policy, the backend flags the citation as invalid or rejects the finding.
2. **No Direct Mutation:** The AI output is treated purely as a proposal (`suggestedWording`). The original `Listing` is never mutated directly by the AI.
3. **No Hallucinated Specifications:** If technical specs are missing, the AI may flag `INCOMPLETE` with severity `LOW`/`MEDIUM`, but is forbidden from inventing hypothetical specs.

## 6. Human-in-the-Loop Workbench & Review Lifecycle

```mermaid
stateDiagram-v2
    [*] --> PENDING: Listing Created / Imported
    PENDING --> VALIDATION_FAILED: Deterministic Checks Fail
    PENDING --> REVIEWING: Deterministic Checks Pass
    
    state REVIEWING {
        [*] --> PolicyRetrieval
        PolicyRetrieval --> LLM_Inference
        LLM_Inference --> CitationVerification
        CitationVerification --> [*]
    }
    
    REVIEWING --> REVIEWING: Retry upon transient failure
    REVIEWING --> NEEDS_CHANGES: Findings Detected
    REVIEWING --> APPROVED: No Findings Detected
    
    state NEEDS_CHANGES {
        InspectFindings --> ApproveSuggestion: Keep AI text
        InspectFindings --> EditSuggestion: Customize text
        InspectFindings --> RejectSuggestion: Dismiss issue
    }
    
    NEEDS_CHANGES --> APPROVED: All critical/high issues resolved & finalized
    APPROVED --> [*]: Ready to publish
```

### Interactive Operations
1. **Approve As-Is:** Accepts `suggestedWording` directly.
2. **Edit & Approve:** Allows the human reviewer to edit the suggestion in an inline editor before approving.
3. **Reject Finding:** Operator dismisses the finding with an optional note (e.g., "Seller provided verified certificate").
4. **Finalize Revision:** Generates a `RevisedListing` snapshot while keeping the original listing intact. The application does not expose update or delete operations for finalized snapshots.
5. **Side-by-Side Diffing:** Visual highlighting (green for additions, red for deletions) of all field changes across Title, Description, Price, and Attributes.

## 7. API Design & Endpoint Specifications

### Listings & Batches
* `POST /api/listings` - Create a single listing (triggers deterministic check).
* `POST /api/batches` - Import a batch of listings (max 20 per batch).
* `GET /api/batches/:id` - Get batch processing summary and status counts.
* `GET /api/listings` - List listings with status/category filters and pagination.
* `GET /api/listings/:id` - Fetch listing details, review records, and revision history.

### Review & Decision Engine
* `POST /api/listings/:id/review` - Trigger or re-run the AI review workflow.
* `GET /api/reviews/:id` - Get full review details, retrieved policy context, and findings.
* `POST /api/reviews/:id/decisions` - Submit operator decisions (`APPROVE`, `EDIT`, `REJECT`) for findings.
* `POST /api/reviews/:id/finalize` - Apply decisions and create the final `RevisedListing`.
* `GET /api/listings/:id/comparison` - Get side-by-side original vs. revised data with diff metadata.

### Policy & Diagnostics
* `GET /api/policies` - Retrieve all policy rules and category guides.
* `GET /api/health` - Service health, DB connectivity, and AI provider status.

| 1 | Project foundation, Prisma schema, and shared contracts | 45–60 minutes |

| 3 | Policy retrieval and structured OpenAI review | 60–90 minutes |

## 10. Scope Boundaries & Non-Goals

To maintain strict adherence to project scope and deliver an exceptional review experience:
* **Excluded:** Real marketplace payment processing / Stripe integration.
* **Excluded:** Real live marketplace publishing / external store webhooks.
* **Excluded:** Image upload and computer vision moderation (text and structured attributes only).
* **Excluded:** Complex multi-tenant seller authentication / OAuth (focus is on review workbench).
* **Excluded:** Unbounded batch queue streaming (batch size is capped at 20 listings).

## 11. Verification & Acceptance Criteria

The system is fully complete and ready when:
1. **Deterministic Layer:** Invalid inputs and duplicates are caught instantly with clear field-level feedback without calling the AI API.
2. **Context Precision:** The AI review only receives relevant policy rules and cannot cite rules outside the retrieved set.
3. **No Unsupervised Mutations:** The AI cannot alter the database listing directly; all revisions require human approval/editing.
4. **Audit Trail:** Original listings, AI findings, operator decisions, and revised listings are preserved through append-only history records and remain viewable. The application exposes no update or delete endpoints for audit events or finalized snapshots.
5. **Resilient Batches:** Batch processing handles mixed valid/invalid listings gracefully without cascading failures.
6. **Documentation & Tests:** All automated tests pass, and complete `README.md`, `AGENT_USAGE.md`, and `.env.example` files are present.
